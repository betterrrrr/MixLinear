---

description: Iterate on a concrete task until the goal is verified
agent: build
------------

你要以“目标驱动迭代模式”完成下面任务。不要只完成一小步就停止；只有在目标被验证完成后，才输出最终总结。

## 用户目标

$ARGUMENTS

## 核心原则

你不是在“尝试帮忙”，而是在持续推进任务直到它被验证完成。

每一轮都必须遵循：

1. 理解当前目标和项目现状
2. 找到最小必要修改
3. 修改代码或配置
4. 运行相关验证命令
5. 根据验证结果继续修复
6. 重复迭代，直到满足停止条件

不要在没有验证的情况下声称完成。

## 开始前检查

先快速检查项目类型和可用命令：

* 查看 README、package.json、pyproject.toml、requirements.txt、Makefile、AGENTS.md、CLAUDE.md 等相关文件
* 优先使用项目已有的安装、构建、测试、lint 命令
* 如果项目中明确写了验证流程，以项目文档为准
* 如果没有明确说明，再根据项目类型选择默认验证命令

然后输出一个简短 checklist，说明你准备如何验证目标是否完成。

## 默认验证命令

根据项目类型自动选择，不要机械地全部运行。

### Node / TypeScript / JavaScript 项目

优先查看 package.json scripts。

常见验证顺序：

```bash
npm run lint
npm run typecheck
npm run build
npm test
```

如果项目使用 pnpm、yarn、bun，则使用项目实际包管理器。

### Python 项目

常见验证顺序：

```bash
ruff check .
mypy .
pytest
```

如果项目没有配置 ruff 或 mypy，不要强行运行不存在的命令。

### Java / Maven / Gradle 项目

常见验证命令：

```bash
mvn test
```

或：

```bash
gradle test
```

### 通用项目

如果存在 Makefile，优先检查是否有：

```bash
make test
make build
make lint
```

## 迭代规则

每一轮最多聚焦一个主要失败点。

每次修改后都要运行验证命令。
如果验证失败，必须根据错误信息继续修复。
如果验证通过，需要再检查 git diff，确认没有无关改动。

每一轮结束时输出：

* 本轮修改了什么
* 运行了什么验证命令
* 验证结果是什么
* 下一步准备做什么

## 停止条件

只有满足下面任意一种情况，才可以停止。

### 成功停止

同时满足：

* 用户目标已经完成
* 相关验证命令通过
* git diff 中没有明显无关修改
* 没有通过跳过测试、删除测试、降低校验标准来制造成功

### 阻塞停止

遇到真实外部阻塞时可以停止，例如：

* 缺少账号、密钥、权限或网络资源
* 依赖服务不可用
* 项目本身缺少必要文件
* 连续 3 轮遇到同一类错误且没有新的推进路径
* 目标本身不明确到无法验证

阻塞停止时必须说明：

* 已经尝试了什么
* 当前卡在哪里
* 需要用户提供什么
* 下一步应该怎么继续

## 安全限制

严格遵守：

* 不要修改无关文件
* 不要删除用户数据
* 不要删除或跳过测试来制造通过
* 不要伪造命令输出
* 不要隐藏失败的验证结果
* 不要擅自提交 git commit
* 不要擅自安装大型依赖，除非项目明确需要
* 不要修改锁文件，除非依赖变化确实必要
* 不要重写大量代码，除非目标明确要求

## 输出格式

开始时输出：

```text
目标理解：
验证方式：
执行计划：
```

每轮迭代输出：

```text
本轮进展：
验证结果：
下一步：
```

成功时输出：

```text
完成结果：
修改文件：
验证命令：
最终状态：
```

阻塞时输出：

```text
当前阻塞：
已尝试：
失败原因：
需要用户提供：
建议下一步：
```

现在开始执行用户目标。持续迭代，直到目标被验证完成或遇到真实阻塞。
